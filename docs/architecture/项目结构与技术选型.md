# 项目结构与技术选型

TestMoon 是测试领域大仓应用集。共享账号、组织、网关及基础库，测试业务作为独立应用接入。以下目录均已有实现；需求统一保存在 `docs/requirements/`。

## 目录与依赖

```text
TestMoon/
├── go.mod / go.sum                  # 唯一 Go module，统一后端依赖
├── package.json / pnpm-lock.yaml
├── pnpm-workspace.yaml              # 根 catalog 管理前端/JS版本
├── Makefile                         # 原生工具的统一构建入口
├── backend/
│   ├── platform/{gateway,identity}/
│   └── testing/{core,execution,mock,runner}/
├── frontend/
│   ├── portal/src/{app,features}/
│   └── testing/src/{app,features,components,hooks,services,models}/
├── libs/
│   ├── go/{platform,transport,testing/domain}/
│   └── frontend/{api,web}/          # 类型化客户端 / 共享 UI 与会话 Hook
├── protocols/
│   ├── platform/identity/v1/
│   └── testing/{contracts,core,execution,mock}/v1/
├── tools/protoc-gen-typescript/     # 从 proto 描述符生成 TS 类型和命名客户端
├── third_party/proto/google/api/
├── deploy/{database,local,runner}/  # 建表定义、中间件与执行镜像
├── scripts/                        # 生成、基础设施、开发启动
└── docs/{requirements,architecture}/
```

Go 服务共享依赖解析，各自具有独立 main 和构建产物。没有服务级 go.mod、go.work 或服务间相互引用 internal 实现。跨服务通过 protobuf gRPC 调用。共享库不依赖具体服务的数据库模型。

前端与 Node Worker 共享 pnpm lockfile/catalog，应用依赖使用 `catalog:`，共享 UI 使用 `workspace:*`。TypeScript/React 类型包版本同样在根 catalog 管理。第三方升级在根目录审阅锁文件后统一完成。


业务服务参考 CodeMatrix 的分层方式，按实际职责建立包：

| 包 | 职责 | 允许依赖 |
| --- | --- | --- |
| cmd/server | 组装服务和生命周期 | conf、logic、api |
| conf | 服务配置入口 | 公共配置组件 |
| api | 实现具体 PB RPC，转交用例逻辑 | PB、logic |
| logic | 授权、业务校验、事务、用例编排 | dao、model、serializer、thirdparty、internal |
| dao | 数据连接、持久化、查询与兼容迁移 | model、基础设施 |
| model | 数据库实体和存储字段 | GORM基础类型 |
| serializer | 领域对象到明确 PB 响应的转换 | PB、传输转换工具 |
| internal | 本服务私有能力，如密码、导入解析、请求校验 | 领域模型、基础库 |
| thirdparty | 外部服务连接及类型化客户端 | 对方公开PB契约 |

HTTP/RPC处理不再经过按操作名分派的通用Handle。logic按具体操作拆文件，资源存储、任务配置和Mock响应由DAO负责。core的跨服务连接由thirdparty统一持有；identity没有外部业务调用，不创建空的thirdparty包。gateway与Runner按各自职责组织，不机械复制数据库服务目录。

前端依赖方向为 app组合路由 → features页面 → hooks/services → `@testmoon/api`。models维护编辑草稿和资源视图模型；components/editors封装请求、脚本、断言、提取、场景步骤与环境编辑，components/resources封装共享资源布局和操作对话框。`@testmoon/web`提供通用布局、会话和UI组件。页面不拼接业务URL或通用操作名；从PB生成的客户端各自接收明确请求类型，编辑状态使用具体类型而非全局Record<string, any>。

## 服务边界

| 进程 | 职责 | 存储边界 |
| --- | --- | --- |
| gateway | Web同域路由、统一认证和CSRF、静态应用、独立Mock域名 | 无业务数据库 |
| identity | 账号密码、会话、组织与组织成员 | testmoon_identity、Redis会话 |
| testing core | 项目及角色、目录、API、用例、场景、环境、快照、导入、文档分享 | testmoon_core |
| execution | 手动任务、执行记录、队列、Outbox、并发、Runner凭证和租约、报告清理 | testmoon_execution、Kafka |
| mock | 端点、条件规则与匿名固定响应 | testmoon_mock |
| Runner supervisor | 主动拉取任务、创建容器、HTTP网络策略、回传结果 | 专属凭证状态文件 |
| per-run worker | 步骤编排、变量、断言、Node脚本 | 单次运行临时内存 |

不将每个 CRUD 拆成单独微服务。核心资源与快照在一个事务边界内，执行调度和不可信脚本独立，匿名 Mock 与业务网关隔离。数据库可在同一 MySQL 实例内；生产凭证应按库隔离，禁止跨库直接查询业务表。

## 数据与授权

所有业务表使用 UUIDv7 字符串主键。通用模型含创建/更新时间和 `soft_delete.DeletedAt`，采用 `softDelete:milli`、0为有效，毫秒时间戳表示删除。初始化使用 AutoMigrate，并在服务开始接收请求前执行兼容迁移；建表快照、字段归属及迁移机制见[数据模型与迁移](数据模型与迁移.md)。后续破坏性变更需单独迁移。

组织即租户，一个账号可加入多个组织。项目由测试应用管理。组织管理员管理所有组织项目；项目管理员管理成员及私有Runner，编辑者维护资源并执行，只读成员查看脱敏内容。平台管理员不隐式获得项目访问权限。

资源表保存公共目录元数据，API、用例、场景、环境和目录定义分别建表，各查询和引用校验使用 org_id + project_id 范围。用例api_id是显式索引字段。目录按资源类型隔离；API与用例独立、场景引用用例或内联请求。编辑采用revision比较，冲突要求重载，不静默覆盖。被引用的API/用例不可直接删除。当前项目只允许删除空项目，存在业务资源、任务、未撤销Runner、Mock或历史记录时拒绝。

密码使用Argon2id；Redis保存随机会话的哈希键，Cookie为HttpOnly、SameSite=Lax，生产开启Secure。改密、重置和禁用通过账号epoch使旧会话失效。内部调用使用服务密钥及带时间戳签名的身份，网关丢弃外部伪造身份头。环境和资源、快照、报告、分享token等敏感内容使用AES-GCM加密；Runner注册及机器凭证只在服务端存哈希。

## 执行与故障

提交执行时读取最新资源并在core事务内固定完整快照。环境变量仅复制到运行，运行修改不回写。execution在同一事务写Run和Outbox；后台发布Kafka，消费者用事件ID去重并条件更新状态。Runner主动拉取，数据库行锁和租户预算约束领取，保证同一运行只被一个节点领取。Kafka不向项目Runner开放。

状态：created → queued → running → passed / failed / unverified / error / timed_out / canceled。未产生断言的步骤为unverified，不能计为通过。场景按步骤串行，默认错误/失败停止当前场景，允许单步继续；任务的测试项串行且变量/Cookie隔离，不同任务可并发。

Runner每5秒心跳，节点30秒未心跳视为离线；领取租约45秒，通过心跳续期。执行中失联变error，离线不能提交，不自动重试或回退。取消通过终态和心跳通知终止容器；已发出的外部HTTP副作用无法撤销。回传采用run_id+node_id+lease，终态不被迟到结果覆盖。

每次执行新建容器：无直接网络、只读、UID10001、去capabilities、no-new-privileges、512MiB内存、1CPU、128PID、64MiB临时目录。Go监督进程执行全部HTTP，公共Runner解析并校验全部DNS结果、拨号固定IP、每次重定向重新检查；不使用环境HTTP代理。私有Runner允许部署网络。Docker API和平台凭证仅留在监督进程。

默认每组织4次并发、每Runner1次（注册1..8）、每次最多100测试项/500总步骤、总超时900秒上限3600、排队300秒。快照≤8MiB、资源≤2MiB、导入≤10MiB；单请求/响应≤1MiB，JS单操作≤10秒、脚本≤64KiB，报告≤8MiB。报告中的请求响应会截断并脱敏。配置见部署文档。

终态报告默认保留30天，后台每小时清理最多1000条；不清理created/queued/running。历史清理为物理删除，普通业务删除为软删除。

## 构建策略

前后端分别原生构建，根Makefile负责聚合。Go每服务产出单独二进制，两个Web应用分别产出dist，Runner/Worker分别产出镜像。协议使用原生protoc生成Go消息、gRPC服务、grpc-gateway桥接、OpenAPI描述及TypeScript类型/命名客户端。Go和OpenAPI与输入同目录；TS输出为libs/frontend/api/src/generated.ts。`make generate`同时更新，生成器代码也在根Go module中。

后续可以将这些边界映射为Bazel target，目前不引入Bazel、CI或自动发布。当前按用户要求不新增单元测试，以编译、生产构建及真实业务联调记录验证边界。
