# 部署配置

## 本地服务

`scripts/local-prepare.sh`准备私有`.env`、本机Runner与Worker镜像；Go/Python 3只用于本机准备，前端在镜像内构建。之后执行：

```bash
docker compose --env-file deploy/local/.env -f deploy/local/compose.yaml up -d --build --wait
./scripts/runner.sh start
```

首次注册通过环境变量`TESTMOON_ENROLLMENT_TOKEN`提供节点凭证，后续沿用`.local/runner.json`。平台恢复后再次执行Runner启动脚本即可，无需重新注册。停止使用`./scripts/runner.sh stop`与同一Compose前缀的`stop`；`down`保留数据卷。停机前等待执行结束，平台持续不可达会让本机Runner退出。

平台应用共用一个镜像，以五个进程容器运行；两份前端静态文件由gateway提供。容器监听`0.0.0.0`，内部使用`identity:8091/9091`、`core:8092/9092`、`execution:8093/9093`、`mock:8094/9094`和`mock:8095`。MySQL/Redis/Kafka使用`mysql:3306`、`redis:6379`、`kafka:9092`；Kafka的宿主机通告地址只供本机客户端使用。

仅gateway与原有中间件端口发布到`127.0.0.1`。浏览器与本机Runner均使用`http://localhost:18080`；业务服务端口、gRPC和Mock raw端口不发布。Worker通过Docker attach与Runner通信，没有直接网络，不需要加入Compose网络。API调用依赖本机Runner的DNS、路由、VPN及证书环境，当前不走HTTP代理。

数据库初始化容器在MySQL健康后幂等创建四库并授权，成功后启动业务服务；gateway等待四个业务服务健康。各业务服务不互相等待，避免core与execution/mock的调用关系造成循环启动依赖。`healthz`为进程就绪检查，实际跨服务链路还需通过登录、Mock与任务执行验证。

保留项目名`testmoon`、`testmoon_mysql-data`、`testmoon_redis-data`、`testmoon_kafka-data`和已有密钥。迁移前运行`./scripts/dev.sh stop`并停止旧Runner；不要在同一端口同时启动两套应用。存在数据卷而缺失`.env`时，准备脚本拒绝生成新密钥，需恢复原配置。凭证轮换需同步调整实际账号；加密密钥更换需要数据迁移。

本机Runner脚本支持`start/stop/status`，日志为`.local/logs/runner.log`，按PID和二进制路径验证进程；遇到同路径的手动Runner会拒绝重复启动。可用`TESTMOON_LOCAL_DIR`指定独立二进制/日志/PID目录，`TESTMOON_RUNNER_STATE`指定注册文件，`TESTMOON_URL`指定平台origin，`TESTMOON_WORKER_IMAGE`指定Worker镜像，`DOCKER_HOST`指定Docker连接。默认使用当前Docker context的地址。自定义网关端口通过`.env`或环境变量`GATEWAY_PORT`设置，需与Runner及Web Origin一致；已注册节点改变origin需使用新的注册文件和节点。

`TESTMOON_ENV_FILE`可指定准备及Runner脚本读取的环境文件；Compose须同步指定`--env-file`。重复准备不会覆盖已有配置。宿主机Runner编译与Worker镜像构建在准备阶段完成，日常Compose不启动常驻Worker。

### 保留的源码开发方式

`scripts/infra.sh up`只启动指定中间件（默认mysql/redis/kafka），生成私有`.env`、等待健康并逐库创建授权。`down`会停止整个同名Compose项目，包括其中运行的应用，保留卷。

| 组件 | 本地监听 | 说明 |
| --- | --- | --- |
| gateway | 127.0.0.1:18080 | Web与独立Mock Host入口 |
| identity | HTTP8091 / gRPC9091 | 内部接口 |
| core | HTTP8092 / gRPC9092 | 内部接口 |
| execution | HTTP8093 / gRPC9093 | 内部接口 |
| mock | HTTP8094 / gRPC9094、raw8095 | raw仅供Mock反代 |
| MySQL | 127.0.0.1:13306 | 四个数据库 |
| Redis | 127.0.0.1:16379 | 密码、会话 |
| Kafka | 127.0.0.1:19092 | 单节点本地KRaft |

`scripts/dev.sh`从私有环境文件读取凭证并设置本地端口/DSN；nohup启动服务，记录PID，逐个检查healthz。stop只终止PID及命令路径匹配本仓库二进制的进程。

## 配置规则

服务支持`--config <yaml>`，优先级：已绑定环境变量 > 指定YAML >代码默认值。环境变量统一以TESTMOON_开头。identity/core/execution/mock/gateway分别通过`TESTMOON_<SERVICE>_HTTP/GRPC/DSN`设置自身地址和数据库。没有通用的服务名自动推导DSN机制；dev.sh显式填入全部本地配置。

常用配置：

| 环境变量 | 含义/默认值 |
| --- | --- |
| TESTMOON_SERVICE_KEY | 内部调用密钥，至少32字符，必填 |
| TESTMOON_ENCRYPTION_KEY | AES-GCM密钥，64位hex，必填；更换需迁移已存数据 |
| TESTMOON_REDIS / REDIS_PASSWORD | Redis地址/密码（前者默认127.0.0.1:6379） |
| TESTMOON_IDENTITY / CORE / EXECUTION / MOCK | 内部gRPC地址，默认9091..9094 |
| TESTMOON_KAFKA | broker地址，dev.sh设为127.0.0.1:19092 |
| TESTMOON_WEB_ORIGIN | 浏览器完整origin，默认http://localhost:8080；dev.sh设18080 |
| TESTMOON_MOCK_HOST | 不带端口的独立Mock Host，默认mock.localhost |
| TESTMOON_MOCK_PUBLIC_HTTP | raw Mock内部监听，默认127.0.0.1:8095 |
| TESTMOON_MOCK_ORIGIN | 可选，界面展示的完整Mock地址；未设则按Web协议/端口与Mock Host推导 |
| TESTMOON_SECURE_COOKIE | 生产true；本地HTTP为false |
| TESTMOON_TLS_CERT / TLS_KEY / TLS_CA | 内部gRPC TLS服务证书/私钥/CA，需SAN匹配实际地址 |
| TESTMOON_LOG_LEVEL | 日志级别，默认info |
| TESTMOON_RETENTION_DAYS | 终态报告保留天数，默认30，必须正数 |
| TESTMOON_ORG_CONCURRENCY | 每组织同时执行数，默认4，范围1..64 |
| TESTMOON_MAX_ITEMS | 单次测试项上限，默认100，范围1..100 |
| TESTMOON_MAX_STEPS | 单次总步骤上限，默认500，范围1..500 |
| TESTMOON_MAX_RUN_SECONDS | 总运行秒数上限，默认3600，范围1..3600 |
| TESTMOON_QUEUE_SECONDS | 最大排队秒数，默认300，必须正数 |
| TESTMOON_BOOTSTRAP_USERNAME / BOOTSTRAP_PASSWORD | 仅identity空账号库时创建初始平台管理员 |

表格缩写变量需补全前缀，例如REDIS_PASSWORD实际为TESTMOON_REDIS_PASSWORD，TLS_KEY实际为TESTMOON_TLS_KEY。配置执行相关限制应在core/execution保持一致。每次执行timeout未填写默认900秒；将最大超时配置为小于900秒时，任务必须显式填入不超过该限制的值。

Runner配置：TESTMOON_URL、TESTMOON_ENROLLMENT_TOKEN（首次）、TESTMOON_RUNNER_STATE、TESTMOON_WORKER_IMAGE。控制面默认只允许HTTPS；本地明确设置TESTMOON_ALLOW_HTTP=1才可HTTP。监督进程使用Docker SDK及DOCKER_HOST等Docker环境配置。注册后凭证与平台origin绑定，切换平台需另建节点及状态卷。

## 生产运行条件

当前交付为应用与本地联调设施，Compose中的单节点Kafka、同一MySQL账号和本地端口不是高可用生产拓扑。生产需要自行提供HTTPS入口、独立Mock域名、私网服务监听、按库数据库凭证、可靠Redis/Kafka、备份与密钥管理。Web Origin需与入口严格一致，启用Secure Cookie；内部gRPC跨不可信网络时配置TLS。网关HTTPS可由入口反代终止，应用内部HTTP不得直接暴露公网。

Kafka服务启动会创建testmoon.execution.v1（三分区，单副本本地默认），生产应预建适当副本数并配置访问控制。本仓库暂未提供Kafka SASL/TLS、多副本部署模板、自动证书签发、监控告警、灾备和容量SLA。这些不能由本地验收推断已满足。

公共与私有Runner均应使用专用Docker执行机器，部署时保证Worker镜像已加载；监督进程Docker权限属于运维权限。私有Runner的网络可达范围由其部署决定；测试平台不会自动建立到用户内网的连接。
